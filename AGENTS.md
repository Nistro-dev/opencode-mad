# AGENTS.md

Guidance for agents working in this repository.

## What this project is

`@fiandev/opencode-kit` is an OpenCode plugin that adds **parallel development
orchestration**: a primary `orchestrator` agent decomposes a task, then subagents
work in isolated git worktrees under `worktrees/`. The plugin enforces agent
permissions (read-only agents, file ownership, worktree scoping) at the tool-call
level.

- Package: `@fiandev/opencode-kit`
- Plugin id: `fiandev.opencode-kit`
- Runtime: OpenCode V2 API — `@opencode/plugin@2.0.23`, `zod@4`
- Plugin source: TypeScript is shipped as source (`main: plugins/main.ts`); only the
  installer is bundled (`install.ts` → `install.js` at `prepack`)
- Package manager / test runner: **Bun** (Node 22 in CI)

## Commands

```bash
bun install              # install deps (CI uses --frozen-lockfile)
bun run typecheck        # tsc --noEmit (plugins/**/*.ts + tests/**/*.ts + install.ts)
bun test                 # node:test suite executed by Bun
bun run test             # alias for bun test
node install.js          # published CLI after a build: install | install -g | update | version
bun install.ts install   # same CLI straight from source, no build needed
```

`bun run typecheck` covers `install.ts` as well; `install.js` is generated by
`bun run prepack`. Before finishing a change, run **both** `bun run typecheck` and `bun test`.

## Plugin architecture (`plugins/`)

The plugin is a small acyclic module tree. Keep it that way: add a tool to its existing
domain module instead of growing a new file, and put shared logic in `lib/`.

```
plugins/
├── main.ts          # package entry (package.json "main") — thin barrel re-exporting
│                    # createPluginHooks, MultiAgentDevPlugin, default. No logic.
├── plugin.ts        # MultiAgentDevPlugin = Plugin.define({ id: "fiandev.opencode-kit", setup })
│                    # wires tools via ctx.tool.transform, the guard via ctx.tool.hook("execute.before"),
│                    # chat.params via ctx.session.hook("context"), and the event subscription.
├── hooks.ts         # createPluginHooks({ directory, log }) — merges all tool domains + hooks
├── types.ts         # shared types incl. ToolDefinition, PluginContext, ToolFactory (leaf module)
├── constants.ts     # PACKAGE_NAME, CURRENT_VERSION, FALLBACK_MODEL, READ_ONLY_AGENTS
├── lib/
│   ├── tool.ts      # local tool() helper
│   ├── errors.ts    # errorMessage / errorOutput
│   ├── glob.ts      # matchGlob
│   ├── util.ts      # firstString / readWorktreeBranch
│   ├── context.ts   # createPluginContext: baseDirectory, runCommand, getGitRoot,
│   │                # getCurrentBranch, logEvent, checkForUpdates
│   ├── registry.ts  # the single process-wide agentPermissions Map + accessors
│   └── guard.ts     # createToolBeforeGuard — tool.execute.before constraint enforcement
└── tools/           # each exports <domain>Tools(ctx): Record<string, ToolDefinition>
    ├── worktree.ts  # worktree_create, status, merge, cleanup, done, blocked, read_task
    ├── quality.ts   # test, final_check
    ├── report.ts    # log, visualize, analyze, create_plan, review
    ├── ci.ts        # check_update, push_and_watch
    ├── agents.ts    # register_agent, unregister_agent
    └── security.ts  # pentest_check_tools, pentest_scan, security_scan
```

Dependency direction is acyclic: `main.ts → plugin.ts → hooks.ts → {lib/*, tools/*}`.
`types.ts` is a leaf and imports only `zod`; `lib/registry.ts` owns the `agentPermissions`
Map and is imported by both `lib/guard.ts` and `tools/agents.ts`. Tools never import
`hooks.ts`, `plugin.ts`, `main.ts`, or each other. Import specifiers inside `plugins/` are
extensionless (`"./types"`, `"../lib/tool"`), so no `tsconfig` change is needed.

### Invariants

- `agentPermissions` stays a single module-level `Map` in `lib/registry.ts`. A second map
  would silently split constraint state between the guard and `register_agent`.
- `plugins/main.ts` stays a thin barrel re-exporting `createPluginHooks`,
  `MultiAgentDevPlugin`, and the default export. The package entry (`main: plugins/main.ts`)
  and `tests/main.test.ts` (which imports `../plugins/main`) rely on it — no logic belongs
  there.
- Tool `description`, `args` schemas, and return strings are the public contract. Changing
  them is a behavior change, not a refactor.

### Entry points and helpers

- `createPluginHooks({ directory, log })` (`hooks.ts`) — builds the testable hook object
  (`tool`, `tool.execute.before`, `chat.params`, `event`) by merging the tool domains in
  `tools/*`. Tests call this directly; no running OpenCode server is needed.
- `MultiAgentDevPlugin` (`plugin.ts`) — `Plugin.define({ id: "fiandev.opencode-kit", setup })`
  wires the hooks into the V2 runtime.
- `tool()` helper (`lib/tool.ts`) — local typed wrapper over a Zod schema (`description`,
  `args`, `execute`) so tool definitions stay compact.
- `createPluginContext` (`lib/context.ts`) — provides `baseDirectory`, `runCommand`,
  `getGitRoot`, `getCurrentBranch`, `logEvent`, and `checkForUpdates` to every tool domain.
- `createToolBeforeGuard` (`lib/guard.ts`) — the `tool.execute.before` constraint enforcement.

### Constraint enforcement

`lib/guard.ts` runs before every tool call and enforces the permissions registered by
`register_agent` (stored in `lib/registry.ts`):

- read-only agents cannot use `edit`, `write`, `patch`, or `multiedit`, and dangerous
  bash commands (`rm`, `mv`, `cp`, redirects, `npm install`, `git commit`, `git push`,
  tag creation) are rejected;
- `allowedPaths` / `deniedPaths` are matched with `matchGlob` from `lib/glob.ts`;
- bash calls for agents bound to a worktree are prefixed with `cd "<worktree>" &&`.

Sessions without registered permissions pass through for backwards compatibility.

## Code style

- TypeScript: 2-space indent, double quotes, **no semicolons**, `strict` mode.
- Prefer Node `fs` APIs over shell interpolation for file operations; use the
  `runCommand` / `getGitRoot` helpers for git and npm. Errors are `unknown`; narrow
  with `errorMessage` / `errorOutput`.
- Keep new dependencies out unless unavoidable — the plugin ships into user projects.
- Markdown: keep tables and headings consistent with existing docs; prose is English.

## Testing

`tests/main.test.ts` uses `node:test` + `node:assert/strict` under Bun. Each test
creates a temporary git repo fixture (`setupRepo`), builds hooks with
`createPluginHooks`, and exercises tools through `getTool(...).execute(...)`.
Cleanup happens in `afterEach`. Extend these fixtures instead of adding new harnesses.

## Release checklist

1. Bump `version` in `package.json` **and** `CURRENT_VERSION` in **`plugins/constants.ts`**
   (they must match).
2. Update `CHANGELOG.md` (Keep a Changelog + SemVer; add compare links).
3. Ensure `package.json` `files` still lists every shipped directory.
4. Run typecheck and tests, commit, tag `vX.Y.Z`, push the tag.
5. CI (`.github/workflows/release.yaml`) only publishes when the tag is on `master`
   and matches the package version.

The `/version-update` command automates steps 1–2; prefer it over manual edits.
